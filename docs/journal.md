# Journal

## 2026-11-19

- Cadrage : problème (les admins Plato organisent les tournois à la main, avec des sites externes et des captures d'écran), périmètre de la v0.1.0, choix de pile, relais, absents et liste d'attente (voir [décisions](decisions.md) D1 à D12).
- Maquettes : direction visuelle « pendule », thèmes sombre et clair.
- PR n°1 (fusionnée) : fondations du dépôt, reprises d'airpost (qualité, CI, hook, documents). Le contrôle gitleaks a d'abord échoué faute de la permission `pull-requests: read` ; corrigé sur ce seul job.
- PR n°8 (en cours) : tournois et inscriptions (voir [décision D15](decisions.md)). Un tournoi appartient à un groupe et toutes ses routes passent par `GroupGuard` (classe entière protégée, `allowOwner` faux). Inscription publique par lien (pseudo seul) : l'inscrit est « en attente » jusqu'à validation par un admin, reçoit un lien personnel pour suivre son statut et annuler ; liste d'attente avec promotion automatique ; pointage. Les validations simultanées sont sérialisées par un verrou de ligne (`SELECT … FOR UPDATE` sur le tournoi) : un test lance 5 validations en parallèle pour 2 places et en attend exactement 2. 26 tests d'intégration, dont l'accès croisé (par le groupe voisin, par son propre groupe avec l'identifiant d'un tournoi ou d'une inscription d'ailleurs, propriétaire de la plateforme, membre retiré). Leçons : (1) un tournoi de 1 place est refusé par la validation (minimum 2) : mes premiers tests en utilisaient un, c'est la validation qui avait raison ; (2) `fetch` refuse un corps sur un GET : le client de test n'en envoie plus.
- PR n°7 (fusionnée) : groupes, rôles et accès croisé (voir [décision D14](decisions.md)). Les rôles de groupe passent dans une table d'appartenance (un compte peut être super admin d'un groupe et admin d'un autre) ; `GroupGuard` est la seule porte d'entrée vers les données d'un groupe et répond 404 identique que le groupe existe ou non. 82 tests dont 48 d'intégration, avec une série « accès croisé ». Leçons : (1) deux fichiers de tests d'intégration en parallèle sur une même base se vidaient mutuellement les tables : `fileParallelism: false`, et la remise à zéro oubliait la nouvelle table `Group` ; (2) des transactions Prisma simultanées échouaient après exactement 2 s (P2028) : non pas un bug de l'application mais `localhost` qui, sur Windows + Docker, tente l'IPv6 avant l'IPv4 et met plus de 2 s à ouvrir chaque nouvelle connexion. Reproduit hors de l'application avec un script de 30 lignes, résolu en écrivant `127.0.0.1` dans les URL ; (3) `prisma migrate diff` a généré des étapes dans un ordre que PostgreSQL refuse (changement d'énumération avant la suppression de la colonne qui en dépend) : migration réordonnée à la main et vérifiée sur une base neuve, puis comparée au schéma.
- PR n°6 (fusionnée) : authentification (voir [décision D13](decisions.md)). Sessions en base avec jeton haché, argon2id, CSRF en deux couches, limites de débit par IP et par compte, invitations et tickets de réinitialisation, script `create-owner`. 67 tests dont 33 d'intégration sur une vraie base PostgreSQL (`iamin_test`, refus de tourner sur une base dont le nom ne finit pas par `_test`), avec un service PostgreSQL ajouté à la CI. Leçons : (1) un verrouillage de compte gardé en mémoire survit d'un test à l'autre : le test dédié a son propre compte ; (2) `cookie` v2 n'est pas résolu avec le module CommonJS du projet : v1 ; (3) une fonction PowerShell qui renvoyait plusieurs valeurs a vidé un fichier de documentation : restauré depuis git, et `git diff --stat` systématique après toute réécriture de fichiers.
- PR n°5 (fusionnée) : `apps/api` (NestJS 11, Prisma 6, PostgreSQL 17 via Docker Compose). Configuration validée au démarrage avec zod (refus d'une origine CORS qui n'est pas exacte, cookie `Secure` obligatoire en production, valeurs jamais affichées dans les erreurs), `helmet`, CORS limité à l'origine de l'interface, sonde `/health` qui ne révèle rien en cas de panne, base exposée sur 127.0.0.1 uniquement. Vérifié pour de vrai avec une base : 200 quand elle répond, 503 quand on l'arrête. Ce test réel a trouvé un bug que les tests unitaires ne voyaient pas : `tsc` ne copiait pas le client Prisma généré dans `dist` (corrigé : le client se charge depuis `@prisma/client`). Le port 5432 était déjà pris sur la machine : `POSTGRES_PORT` rend le port configurable. Les scripts d'installation de pnpm 10 sont bloqués par défaut : seuls ceux de Prisma sont autorisés (`onlyBuiltDependencies`). L'audit de la CI a refusé deux failles « high » dans l'outil `prisma` (`deepmerge-ts` et `effect`, utilisés pour sa config, pas par l'API en marche) : forcées vers les versions corrigées avec `overrides` dans `pnpm-workspace.yaml`, à retirer quand Prisma les relèvera.
- PR n°4 (fusionnée) : générateurs de texte pour le chat dans `@iamin/engine` (inscrits et liste d'attente, VS d'un tour ou d'une journée, résultats, classement). Texte brut, un fait par ligne. Les pseudos viennent d'inscriptions publiques : nettoyés (retours à la ligne et caractères de contrôle supprimés) pour qu'un pseudo ne puisse pas ajouter de fausses lignes au message copié (risque R10).
- PR n°3 (fusionnée) : ligue dans `@iamin/engine`. Calendrier par la méthode des cercles (repos tournant si le nombre de joueurs est impair, aller-retour en option). Classement : points, confrontation directe, différence de score, score marqué, puis ordre du tirage. Leçon : réécrire un fichier avec `Get-Content` puis `Set-Content` sous PowerShell 5.1 a corrompu les accents (lecture en ANSI) ; lecture et écriture en UTF-8 explicite désormais, et `git diff --stat` avant de continuer.
- PR n°2 (fusionnée) : paquet `@iamin/engine`, arbre d'élimination directe. Tirage vérifiable : identifiants triés puis mélange de Fisher-Yates avec une graine, donc le résultat ne dépend pas de l'ordre d'inscription. Les byes vont aux têtes de série 1 à N (des joueurs tirés au sort), jamais deux dans le même match.
