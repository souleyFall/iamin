- PR n°13 (en cours) : page publique et PWA installable (voir [décision D20](decisions.md)). Page `/t/:slug` sans compte : inscription, statut du joueur retrouvé grâce à son lien gardé sur l'appareil, tours, scores, classement et graine en direct (SSE de D18) ; lien à partager dans l'onglet Inscrits ; manifeste, icônes et service worker sans plugin. Leçons : (1) l'essai réel a trouvé un bug que aucun test ne voyait : le CORS de l'API n'autorisait pas l'en-tête `x-player-token`, donc l'inscription passait mais la lecture du statut échouait dans le navigateur ; les tests d'API n'envoient pas d'`Origin`, un test de préambule CORS le garde désormais ; (2) le message du direct relisait la vue mais pas l'inscription du joueur : sa carte restait sur « en attente » ; (3) `NODE_ENV=development` laissé dans mon terminal a produit un build de développement (pas de service worker) : toujours fixer `production` avant de construire ; (4) le volet navigateur de l'application refuse d'enregistrer un service worker (« unknown error ») : manifeste, icônes et script vérifiés par leurs réponses HTTP, l'enregistrement reste à confirmer sur un vrai téléphone.
- PR n°12 (fusionnée) : interface admin, `apps/web` (voir [décision D19](decisions.md)). React + Vite, jetons de design de la maquette, écrans de connexion, de liste, de création, d'inscrits, de pointage, de tirage, de matchs avec la feuille de saisie du score, de journal et de copie pour le chat. Essayée pour de vrai (API réelle, navigateur, téléphone émulé) : connexion entre deux origines, création, pointage, tirage, score. 31 tests de l'interface. Leçons : (1) un test a trouvé un vrai bug : recharger la page d'un tournoi renvoyait à la liste, car l'écran jugeait l'accès avant l'arrivée de la liste des groupes ; (2) l'essai réel a trouvé le second : la feuille de saisie affichait « Match 0 » (un indice cherché par identité d'objet, recréé à chaque lecture) ; (3) `@testing-library/jest-dom` 8 ne s'accorde pas avec les types de Vitest 4 (`expect` devenait `any` pour ESLint) : on s'en passe, assertions simples ; (4) le moteur est en CommonJS, Vite doit être réglé pour le convertir.

- PR n°11 (fusionnée) : page publique et direct (voir [décision D18](decisions.md)). Deux routes publiques en lecture seule (vue du tournoi, flux SSE). Le serveur n'est pas prévenu par les services d'écriture : il compte les événements du journal validés en base, donc aucune annonce avant la validation et rien à ajouter ailleurs. 8 tests d'intégration, surtout sur ce que la page ne montre pas (inscriptions en attente, jetons, détenteur, versions). Leçon : l'identifiant interne d'un tournoi (un uuid) a la forme d'un lien valide, donc il répond 404 et non 400 ; c'était mon test qui avait tort.
- PR n°10 (fusionnée) : relais entre admins et journal d'événements (voir [décision D17](decisions.md)). Toute écriture sur un tournoi exige d'en tenir la main, vérifié sous le verrou de ligne ; proposition et acceptation du relais, reprise par le super admin, journal écrit dans la même transaction que le changement, version des scores contre les écrans périmés. 142 tests dans l'API (17 nouveaux), dont l'accès croisé sur les 7 routes de relais et de journal. Leçons : (1) le journal ne contient aucun pseudo (identifiants seulement), sinon annuler une inscription aurait laissé le pseudo dans l'historique, en contradiction avec le registre RGPD ; (2) en PowerShell, un mot précédé d'un accent grave (par exemple `version`) dans une chaîne entre guillemets est lu comme une séquence d'échappement : deux tabulations verticales se sont glissées dans des commentaires, repérées par la règle `no-irregular-whitespace` d'ESLint ; (3) un test de concurrence de la PR n°9 faisait écrire deux admins en parallèle : il est devenu faux avec le relais, et a été réécrit avec deux onglets du même admin.
- PR n°9 (fusionnée) : tirage, scores, forfaits et remplacements (voir [décision D16](decisions.md)). L'API utilise enfin le moteur `@iamin/engine`. Le tirage est fait par le serveur avec une graine aléatoire qu'il choisit, publiée avec la liste triée des joueurs : un test refait le tirage avec le moteur et compare. Les scores avancent les vainqueurs (élimination) ou alimentent le classement (ligue) ; un forfait donne un score par défaut réglable au vainqueur. 125 tests dans l'API (17 nouveaux), dont l'accès croisé sur les 5 routes de matchs, par le groupe voisin, par son propre groupe avec l'identifiant d'un tournoi ou d'un joueur d'ailleurs, propriétaire et anonyme. Leçons : (1) les tests ont trouvé un vrai bug : annuler le score d'un match dont le match suivant était déjà joué faisait lever une erreur du moteur non traduite (500 au lieu de 409), corrigé en testant le match suivant avant de recalculer ; (2) le moteur est maintenant une dépendance de l'API : `tsc` et `eslint` (règles typées) lisent son `dist`, donc il est construit à l'installation (`postinstall`) et au début de `pnpm check`, sans quoi `lint` échoue sur une CI neuve.
- PR n°8 (fusionnée) : tournois et inscriptions (voir [décision D15](decisions.md)). Un tournoi appartient à un groupe et toutes ses routes passent par `GroupGuard` (classe entière protégée, `allowOwner` faux). Inscription publique par lien (pseudo seul) : l'inscrit est « en attente » jusqu'à validation par un admin, reçoit un lien personnel pour suivre son statut et annuler ; liste d'attente avec promotion automatique ; pointage. Les validations simultanées sont sérialisées par un verrou de ligne (`SELECT … FOR UPDATE` sur le tournoi) : un test lance 5 validations en parallèle pour 2 places et en attend exactement 2. 26 tests d'intégration, dont l'accès croisé (par le groupe voisin, par son propre groupe avec l'identifiant d'un tournoi ou d'une inscription d'ailleurs, propriétaire de la plateforme, membre retiré). Leçons : (1) un tournoi de 1 place est refusé par la validation (minimum 2) : mes premiers tests en utilisaient un, c'est la validation qui avait raison ; (2) `fetch` refuse un corps sur un GET : le client de test n'en envoie plus.
- PR n°7 (fusionnée) : groupes, rôles et accès croisé (voir [décision D14](decisions.md)). Les rôles de groupe passent dans une table d'appartenance (un compte peut être super admin d'un groupe et admin d'un autre) ; `GroupGuard` est la seule porte d'entrée vers les données d'un groupe et répond 404 identique que le groupe existe ou non. 82 tests dont 48 d'intégration, avec une série « accès croisé ». Leçons : (1) deux fichiers de tests d'intégration en parallèle sur une même base se vidaient mutuellement les tables : `fileParallelism: false`, et la remise à zéro oubliait la nouvelle table `Group` ; (2) des transactions Prisma simultanées échouaient après exactement 2 s (P2028) : non pas un bug de l'application mais `localhost` qui, sur Windows + Docker, tente l'IPv6 avant l'IPv4 et met plus de 2 s à ouvrir chaque nouvelle connexion. Reproduit hors de l'application avec un script de 30 lignes, résolu en écrivant `127.0.0.1` dans les URL ; (3) `prisma migrate diff` a généré des étapes dans un ordre que PostgreSQL refuse (changement d'énumération avant la suppression de la colonne qui en dépend) : migration réordonnée à la main et vérifiée sur une base neuve, puis comparée au schéma.
- PR n°6 (fusionnée) : authentification (voir [décision D13](decisions.md)). Sessions en base avec jeton haché, argon2id, CSRF en deux couches, limites de débit par IP et par compte, invitations et tickets de réinitialisation, script `create-owner`. 67 tests dont 33 d'intégration sur une vraie base PostgreSQL (`iamin_test`, refus de tourner sur une base dont le nom ne finit pas par `_test`), avec un service PostgreSQL ajouté à la CI. Leçons : (1) un verrouillage de compte gardé en mémoire survit d'un test à l'autre : le test dédié a son propre compte ; (2) `cookie` v2 n'est pas résolu avec le module CommonJS du projet : v1 ; (3) une fonction PowerShell qui renvoyait plusieurs valeurs a vidé un fichier de documentation : restauré depuis git, et `git diff --stat` systématique après toute réécriture de fichiers.
- PR n°5 (fusionnée) : `apps/api` (NestJS 11, Prisma 6, PostgreSQL 17 via Docker Compose). Configuration validée au démarrage avec zod (refus d'une origine CORS qui n'est pas exacte, cookie `Secure` obligatoire en production, valeurs jamais affichées dans les erreurs), `helmet`, CORS limité à l'origine de l'interface, sonde `/health` qui ne révèle rien en cas de panne, base exposée sur 127.0.0.1 uniquement. Vérifié pour de vrai avec une base : 200 quand elle répond, 503 quand on l'arrête. Ce test réel a trouvé un bug que les tests unitaires ne voyaient pas : `tsc` ne copiait pas le client Prisma généré dans `dist` (corrigé : le client se charge depuis `@prisma/client`). Le port 5432 était déjà pris sur la machine : `POSTGRES_PORT` rend le port configurable. Les scripts d'installation de pnpm 10 sont bloqués par défaut : seuls ceux de Prisma sont autorisés (`onlyBuiltDependencies`). L'audit de la CI a refusé deux failles « high » dans l'outil `prisma` (`deepmerge-ts` et `effect`, utilisés pour sa config, pas par l'API en marche) : forcées vers les versions corrigées avec `overrides` dans `pnpm-workspace.yaml`, à retirer quand Prisma les relèvera.

- PR n°2 (fusionnée) : paquet `@iamin/engine`, arbre d'élimination directe.
